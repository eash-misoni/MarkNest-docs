IssueとPull Requestの進め方

本文の用語リンクから意味・画面での場所を確認できます。

知らない言葉は、本文中の点線付きリンクをクリックすると解説ページへ移動できます。ブラウザの「戻る」で読んでいた位置へ戻れます。

以下は実際の作業開始後に使う手順です。知らない用語は、その場の用語リンクから確認してください。

Issueを開いたら読む順番

  1. 目的：何ができるようになればよいのか。
  2. 入力と出力：どのデータ型・公開関数・画面を使うか。
  3. 今回やらないこと：意図しない仕様拡大を防ぐ。
  4. 依存関係：前の作業が必要か。モックで先に進められるか。
  5. 完成条件：どのテスト・操作・ログで合格と言えるか。
  6. 設計資料：r3総合ガイドの章と、必要ならExcelのシート名。
  7. テスト資料：完成条件に対応するテストケースがあるかを確認する。

疑問点をIssueへ書くときは「現状」「期待する動作」「確認したコード・資料」「何を決めてほしいか」を分けると伝わりやすくなります。

Issue着手時：テスト資料を探す

テスト資料の入口（docs/testing/README.md）から、目的に応じて次の2冊を確認します。

資料 どんなときに使う？
CIテスト設計書 ci-test-plan.xlsx（CT-） 担当する関数・公開契約・失敗条件について、自動テストの候補と期待結果を確認するとき。設計済みのケースすべてがコード化・実行済みとは限りません。
システムテスト仕様書 system-test-spec.xlsx（ST-） 画面操作や機能全体の振る舞いをChrome実機などで確認するとき。学校提出用の資料で、CIとは別に実行条件と結果を管理します。

探し方： Issueの完成条件を読む → 対象の操作・関数・状態変化を特定する → 2冊の該当するST-／CT-ケースを探す → テスト方法と期待結果を確認する。該当IDが見つからない場合は、勝手に結果を埋めず、IssueやPRで「該当ケース未特定／追加案」として相談します。仕様とテストの期待値が食い違う場合も独断で書き換えません。

このリンクはGitHub上の正本を開きます。ローカルでWikiを開いていても使えますが、ネット接続とPrivateリポジトリへのアクセス権が必要です。

変更の粒度

原則として1 Issue = 1ブランチ = 1PR。ただしファイル数を機械的に小さくするのではなく、動く成果としてテストできる単位にします。関連のない修正は別Issueへ。新たな公開API・DB契約が必要なら、先に関係する担当者と確認します。

Gitの操作例

git switch main
git pull --ff-only
git switch -c feat/issue-XX-short-description
# 編集・テストした後
git status
git add <変更したファイル>
git commit -m "feat: describe change for issue XX"
git push -u origin feat/issue-XX-short-description

git switch mainはmainへ移動、git pull --ff-onlyはGitHub側の最新状態を取り込み、git switch -cは新しい作業ブランチを作成します。git addで記録対象を選び、git commitで変更履歴を作り、git pushでGitHubへ送ります。Gitのpull（プル）はリモートから取得する操作で、Pull Request（PR）とは別です。

XXは実際のIssue番号に置き換えます。既存のブランチ運用やリポジトリの指示が異なる場合はそちらを優先します。push後、GitHubでPRを作り、関連Issueを記載します。

PR本文の最小テンプレート

関連Issue: #XX
目的: 何を実現する変更か
実装したこと: どの機能・ファイルを変更したか
対象外: 今回やっていないこと
確認: 実行したコマンド／Chromeで試した操作／期待と実際
仕様根拠: r3の章・型・関数・シート
未確認: AWS実機、権限、異常系など残る事項

テストIDと結果の書き方（記入例）

次は説明用の架空ID・架空の結果です。実際のPRでは、テスト設計書に載っているIDと本当に実施した結果に置き換えてください。

関連Issue: #XX（自分のIssue番号に置換）
関連テスト: CT-EXAMPLE-01（仮：関数の空入力）／ST-EXAMPLE-01（仮：画面表示）
実施したテスト: npm run check（ローカル）、CT-EXAMPLE-01相当の自動テスト
結果: 上記の実行は合格（仮の記入例。PRのCI結果は別途Checksで確認）
未確認: ST-EXAMPLE-01（Chrome実機テストは未実施。環境準備後に確認）

CT-の対応テストコードがまだなければ「テストコード未作成」、ST-を実行していなければ「未実施」と記します。CI成功は、Chrome実機やAWSで動いたことの保証ではありません。 実機検証の対象と未検証をPR本文で区別しましょう。Codexの自動レビューでは不具合・設計の責務・可読性・テストの妥当性を確認します（AIとコードレビュー）。指摘は必須修正／改善推奨／学習メモに分け、軽微な提案を無条件のマージ条件にしません。人の確認と権限者によるマージを待ちます。
