IssueとPull Requestの進め方

本文の用語リンクから意味・画面での場所を確認できます。

知らない言葉は、本文中の点線付きリンクをクリックすると解説ページへ移動できます。ブラウザの「戻る」で読んでいた位置へ戻れます。

このページでは、担当する作業が決まってから、コードの変更をGitHubへ提出してレビューを受けるまでを説明します。Issueは作業の依頼書、Pull Request（PR）は変更したコードを取り込んでもらうための申請です。

全体の流れは開発フロー、PCの準備はローカル環境を先に参照してください。

1. Issueを開いて、何をするか理解する

MarkNest Development（Project #3）から未割り当てのReady Issueを選び、タイトルをクリックして詳細を開きます。実際のIssue #7は過去の作業例です。GitHubへのログインと本体リポジトリへのアクセス権が必要です。

Issueのタイトル横には番号（例：#7）が表示されます。本文を読み、次の項目を確認しましょう。

項目 何を確認する？
目的 何ができるようになればよいか
入力と出力 どのデータ型・公開関数・画面を使うか
今回やらないこと どこまで変更してよいか。関係ない機能を変えない
依存関係 先に必要な作業がないか。モックで進められるか
完成条件 何ができれば作業が完了したと言えるか
設計資料 r3総合ガイドのどの章、Excelのどのシートを読むか
テスト資料 どうやって動作を確認するか

分からないことがあるときは、Issue下部のコメント欄に「現状」「期待する動作」「確認したコード・資料」「何を決めてほしいか」を書いて相談します。分からない仕様を推測で決めないでください。

作業を引き受けるときは担当者が未設定でReadyであることを再確認し、Issue右側のAssigneesに自分を設定します。ProjectのStatusをIn Progressへ変更します。

2. 設計資料とテスト資料を確認する

Issueだけでは、関数の名前や入力・戻り値などがすべて分からない場合があります。設計資料から該当する設計書を読み、使う型・関数と処理のルールを確認してから実装します。公開APIやDBの契約を変更する必要があれば関係する担当者と相談します。

テスト資料の入口（docs/testing/README.md）には、次の2冊があります。

資料 どんなときに使う？
CIテスト設計書 ci-test-plan.xlsx（CT-） 関数の入力・出力・エラーなど、自動テストで確認する内容と期待結果を調べる
システムテスト仕様書 system-test-spec.xlsx（ST-） 画面操作や機能全体の動作をChrome実機などで確認する。学校提出用の資料で、CIとは別に条件と結果を管理する

例えば、ある関数の処理を作るなら、その関数名や動作に対応するCTのケースを探します。画面操作を作るなら対応するSTも確認します。テストIDはそれぞれの確認項目に付いている番号です。

完成条件から対象の操作・関数・状態変化を特定し、対応するID、テスト方法、期待結果を確認します。設計済みのケースがすべてコード化・実行済みとは限りません。該当IDが見つからなければ「該当ケース未特定／追加案」としてIssueやPRで相談します。仕様と期待値が食い違う場合も独断で変更しません。

3. 自分専用のブランチを作る

mainはチーム全員が共有する正式なコードです。他のメンバーが同時に作業しても影響しないように、自分の作業用ブランチを作ります。原則として 1 Issue = 1ブランチ = 1PR です。関連のない修正は別Issueに分けます。ファイル数ではなく、動作を確認できる成果単位で作業してください。

VS CodeでMarkNestフォルダを開き、「ターミナル」→「新しいターミナル」で作業します。すでにclone済みであることが前提です。次のコマンドを1行ずつ実行します。

git status
git switch main
git pull --ff-only
git switch -c feat/issue-XX-short-description
  • git status：現在のブランチと未記録の変更を確認します。変更が残っていたら、消したり無理に切り替えたりせず先に相談してください。
  • git switch main：mainに移動します。
  • git pull --ff-only：GitHub上の最新のmainを取り込みます。失敗した場合は原因を確認し、無理に上書きしません。
  • git switch -c：今のmainから新しい作業用ブランチを作って移動します。

最後のブランチ名は例です。XXを担当Issue番号に、short-descriptionを短い作業名に置き換えます。例えばIssue #12ならfeat/issue-12-display-titleのようにします。リポジトリやIssueで指定された命名があればそちらを優先してください。

もう一度git statusを実行し、作成したブランチ名が表示されることを確認してください。mainのまま編集を始めないようにします。

4. コードを編集し、テストする

Issueと設計資料を見ながら、エディタで担当するファイルを編集・保存します。必要な自動テストを追加・修正し、ローカルで検査します。起動確認の手順とコマンドはローカル環境を参照してください。

完成条件に対応するテストを実行し、期待した動作になったか確認します。実機確認が必要な場合は専用プロフィール・ダミーデータを使用します。実行していないテストは合格にしません。

5. 変更をcommit・pushする

commitは変更をGitの履歴に記録する操作、pushはその履歴をGitHubへ送る操作です。エディタで保存しただけではGitHubには送られません。

まず次を実行します。

git status
git diff

変更したファイルが自分の担当範囲内か確認します。git diffはまだステージしていない変更を表示します。新規ファイルの内容はエディタで確認し、追加後の差分も確認してください。

git add <変更したファイル>
git diff --cached
git commit -m "feat: describe change for issue XX"
git push -u origin feat/issue-XX-short-description

上のコマンドには置き換える箇所があります。山括弧を含めてそのまま入力しないでください。例えばextension/popup.jsを変更した場合はgit add extension/popup.jsと入力します。複数の担当ファイルがある場合はそれぞれ追加します。

  • git add：今回記録するファイルを選びます。無関係なファイルや認証情報を追加しません。
  • git diff --cached：commitに含まれる変更を確認します。表示が長い場合はqで終了できます。
  • git commit -m：変更内容を説明する短いメッセージを付けて履歴を作ります。メッセージも自分の作業に合わせて変更します。
  • git push -u origin：GitHubの自分の作業ブランチへ送ります。ブランチ名は手順3と同じ名前にします。

pushが成功したら、GitHubで作業ブランチのファイルを確認できます。Gitのpull（プル）は変更をPCに取り込む操作、pushは送る操作です。Pull Requestとは別です。

6. GitHubでPRを作成する

ここからはブラウザで操作します。MarkNestのPull requestsを開きます。

  1. Compare & pull requestが表示されていればクリックします。表示されなければNew pull requestを押します。
  2. baseをmain、compareを自分がpushした作業ブランチに設定します。baseは取り込み先、compareは今回の変更元です。
  3. 表示された差分を読み、無関係な変更が含まれていないことを確認します。
  4. Create pull requestへ進み、タイトルと本文を書きます。タイトルは何を作ったか分かる名前にします。
  5. 内容を確認してCreate pull requestを押します。作成したらProjectのStatusをIn Reviewへ変更します。

PRを作っただけでは、まだmainには変更されていません。 ここから自動検査とレビューを受けます。

PR本文に書くこと

既存のPRテンプレートを使い、例示の番号や空欄を自分の作業内容に置き換えます。まず次の項目を説明できれば十分です。

関連Issue: #XX
目的: 何を実現する変更か
変更内容: どの機能・ファイルを変更したか
対象外: 今回やっていないこと
仕様根拠: r3の章・型・関数・シート
確認: 実行したコマンド／Chromeで試した操作／期待と実際
未確認: 実行していないテスト・残る課題

関連Issue番号を実際の番号に置き換えると、レビュー担当者が作業の依頼内容を確認しやすくなります。Closes #番号はmainへのマージ時にIssueを自動で閉じる記法です。受け入れ条件がまだ残っている場合は、勝手に閉じずRefs #番号などで関連付け、人間の完了確認を待ちます。

テストIDと結果の書き方（記入例）

以下は説明用の架空ID・架空の結果です。実際のPRでは、テスト設計書に載っているIDと本当に実施した結果に置き換えます。

関連Issue: #XX（自分のIssue番号に置換）
関連テスト: CT-EXAMPLE-01（仮：関数の空入力）／ST-EXAMPLE-01（仮：画面表示）
実施したテスト: npm run check（ローカル）、CT-EXAMPLE-01相当の自動テスト
結果: 上記の実行は合格（仮の記入例。PRのCI結果は別途Checksで確認）
未確認: ST-EXAMPLE-01（Chrome実機テストは未実施。環境準備後に確認）

CTの対応テストコードがまだなければ「テストコード未作成」、STを実行していなければ「未実施」と記します。CI成功はChrome実機やAWSで動いたことの保証ではありません。

7. CIとレビュー結果を確認する

作成したPRを開くと、主に次のタブがあります。過去のPR #17で見比べることもできます。

タブ 何を見る？
Conversation PR本文、レビューコメント、全体の状況
Commits 追加した変更履歴
Checks GitHub Actionsが実行したCIの結果
Files changed 追加・削除・変更したコードと、その行への指摘

Checksで成功・失敗・実行中を確認します。失敗した場合は失敗したジョブを開き、ログの最初のエラーから調べます。成功しても人間のレビューは必要です。Codexのレビューでは不具合、責務、可読性、テストの妥当性などを確認します。

指摘の扱いは必須修正／改善推奨／学習メモに分かれます。軽微な提案をすべて無条件に修正する必要はありません。詳しくはAIとレビューを参照してください。

8. 指摘を受けたら、同じPRを修正する

レビューコメントを読み、必要な修正をPCの同じ作業ブランチに加えて保存します。テストを再実行し、修正したファイルをgit add、git commit、git pushの順に操作します。

最初のpushで追跡先を設定していれば、次回からgit pushだけで同じブランチへ送れます。新しいコミットは既存のPRに自動で追加されます。PRを作り直したり、mainへ直接pushしたりする必要はありません。

修正内容と再確認の結果をPRのコメントで伝えます。指摘の意味が分からなければ質問してから修正します。

9. マージと作業の完了

必要なテスト・レビュー・完成条件を人間が確認し、権限のある人がmainへマージします。レビュー担当は原則として実装者以外の人です。承認前に自分の判断でマージしません。

マージされたら、受け入れ条件の確認とIssueのClose／ProjectのDoneを確認します。マージ済みでも受け入れ未完了なら、残る作業を明確にします。次の作業を始めるときは、未割り当てReady Issueを選び、最新のmainから新しいブランチを作ります。

困ったとき

Gitコマンドのエラー、差分の衝突、CIの失敗などで進めなくなったら、無理に上書きせず困ったときを確認します。続行できない場合はIssueに原因・影響・必要な判断を記録し、StatusをBlockedにします。秘密情報はログやスクリーンショットに含めないでください。
