開発フロー：ReadyからDoneまで

本文の用語リンクから意味・画面での場所を確認できます。

知らない言葉は、本文中の点線付きリンクをクリックすると解説ページへ移動できます。ブラウザの「戻る」で読んでいた位置へ戻れます。

MarkNestでは、メンバーが作業を自分で選び、実装・テストをして提出し、確認を受けて完了させます。1つの作業を始めてから終えるまでの流れを、順番に説明します。

全体の流れ

Issueを選ぶ → 担当登録 → ブランチ作成 → 仕様・設計の確認 → 実装・テスト → commit・push → PR作成 → レビュー・修正 → マージ・完了

1. 担当する作業を選ぶ

MarkNest Development（Project #3）を開き、StatusがReadyで、担当者がまだ設定されていないIssueを探します。MarkNestは自分で担当を選ぶ方式です。

Issueの目的・作業範囲・完成条件・依存関係・確認方法を読み、着手できるか判断します。内容や前提が分からなければ、始める前に質問してください。PriorityがHighでも、Backlogの作業に勝手に着手しません。

2. 担当登録をする

他のメンバーが担当していないことを再確認し、IssueのAssigneesに自分を設定します。ProjectのStatusをIn Progressへ変更します。これで、今は自分がその作業を進めていることが伝わります。

3. 作業用ブランチを作る

PCで最新のmainを取得し、自分の作業用ブランチを作ります。原則として1 Issueにつき1ブランチ・1PRです。mainへ直接変更を書き込みません。具体的な操作はIssueとPRを確認してください。

4. 仕様書・設計書・テスト仕様書を確認する

実装を始める前に、Issueに関連付けられた資料を読みます。仕様書で何を実現するか、内部設計書でどの型・関数を使うか、テスト資料でどう確認するかを把握します。資料とコードが矛盾する場合は独断で仕様を変えません。

参照先：設計資料／テスト資料の入口。

5. 実装し、手元でテストする

担当範囲のコードを作成します。既存の公開契約やJSDocの型定義を守り、必要なテストを追加・修正します。ローカルで動作・構文・型・テストを確認し、Issueの完成条件と照合します。

確認に使うコマンドはローカル環境を参照してください。CIで確認できるものとChrome・AWSなどの実機確認は別です。

6. commit・pushし、PRを作る

変更したファイルを確認してcommitし、作業ブランチをGitHubへpushします。mainを取り込み先とするPRを作り、関連Issue、変更内容、参照した資料、テスト結果、未確認事項を書きます。ProjectのStatusをIn Reviewへ変更します。

PRは変更内容を確認してもらうための提出物であり、作成しただけでは作業完了ではありません。

7. CIとレビューに対応する

PRのChecksでCIの結果を確認し、Codexと人間によるコードレビューを受けます。通常は実装担当者以外のメンバーが確認します。指摘やテスト失敗があれば、同じブランチを修正し、再度commit・pushして必要なテストを実行します。新しいPRを作り直す必要はありません。

CIが成功しても、仕様どおり動作することや実機検証の完了を保証するわけではありません。詳しくはAIとレビューを参照してください。

8. マージ・完了確認

必要なテスト、レビュー、Issueの完成条件を人間が確認し、問題なければ権限のある人がmainへマージします。受け入れ条件を満たしたことを確認したうえで、IssueをCloseするかProjectのStatusをDoneへ変更します（DoneにするとIssueも自動Closeされます）。

PRがマージされたことだけで、機能全体の受け入れが完了したとは限りません。親Issueは子IssueがすべてClosedになっても無条件にDoneにはしません。人間の確認なしにAIへマージ・Done操作を任せません。

完了を確認したら、次の未割り当てReady Issueを探します。

途中で進めなくなった場合

仕様が不明、依存先が未完成、テストが失敗して解決できないなどの場合は、原因・影響・必要な判断をIssueに記録し、続行できないときはStatusをBlockedにします。詳しくは困ったときを参照してください。

各Statusの意味はStatusの用語解説、管理AIのReady補充やマージ後の文書確認はAIとレビューで確認できます。
