開発フロー：ReadyからDoneまで

本文の用語リンクから意味・画面での場所を確認できます。

知らない言葉は、本文中の点線付きリンクをクリックすると解説ページへ移動できます。ブラウザの「戻る」で読んでいた位置へ戻れます。

MarkNestはメンバーが作業を選ぶ「プル型」です。先に全員へ担当を固定して振り分ける運用ではありません。

Statusをどう読むか

これらの値はMarkNest Development（Project #3）で確認します。 BacklogやReadyはStatusという欄の選択肢です。HighなどのPriorityと混同しないでください。各用語のリンク先に、画面上の確認場所も書いてあります。

Status どういう状態か メンバーの行動
Backlog 採用済みだが着手の条件が不十分・未確認 無理に始めず、必要な前提を確認
Ready 仕様・依存・確認方法が揃った未割り当ての着手可能Issue 自分で選び、着手時にAssigneeを設定
In Progress 担当者が実装・検証中 進捗や阻害要因をIssueに残す
In Review PR作成済みでCI・AI・人の確認を受けている レビューへ対応し、必要なテストを再実行
Blocked 続行を妨げる問題が確認された 原因・影響・必要な判断を記録
Done 完成条件と必要な受け入れ確認を満たした 人による確認後にClose／Doneへ

注意： GitHub IssueのOpen/Closed、ProjectsのStatus、Priority（High/Medium/Low）は別の概念です。「OpenだからReady」「Highだから今着手できる」と判断しません。

Readyプールの目安

AIマネージャーは未割り当てReadyを通常5〜6件維持することを目標にします。4件以下なら補充を検討します。ただし、数合わせで未確定仕様を起票したり、Blockedの作業をReadyにしたりしません。日次タスクのGitHub書き込み成功は毎回検証が必要です。

一連の基本手順

Ready（自分で選ぶ） → Assignee設定／In Progress → ブランチ作成 → 実装・検査 → PR → In Review → 人間による受け入れ → Done／Close

  • レビュー担当を特定の一人に固定する必要はありませんが、通常は実装担当者以外のメンバーが確認します。
  • PRがマージされたというだけで、機能全体の受け入れが済んだとは限りません。親Issueは子Issueが全部Closedになっただけで自動的にDoneにしません。
  • StatusをDoneへ移すとIssueが自動Closeする連動があります。本人・レビュー担当・権限者の確認なしにAIへDone操作を委ねません。
