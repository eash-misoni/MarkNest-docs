アーキテクチャ：誰が何を持つ？

本文の用語リンクから意味・画面での場所を確認できます。

知らない言葉は、本文中の点線付きリンクをクリックすると解説ページへ移動できます。ブラウザの「戻る」で読んでいた位置へ戻れます。

MarkNestはChrome拡張が主体です。ブックマークの実体とフォルダはChromeが管理し、MarkNestが読み取って分類案を提示します。AWSは任意のグループ設定同期を担い、分類モデル本体をサーバーへ置くという決定ではありません。

Chrome拡張（JavaScript / Manifest V3）
  ├─ UI / main                画面・入力と各機能の呼び出し
  ├─ ClassificationSession  今回の仮所属と仮設定
  ├─ classificationModel    ページ情報・Embedding・分類
  ├─ groupService           グループと子フォルダ対応
  ├─ bookmarkService        Chrome Bookmarks APIの読取・作成・移動
  ├─ applyService           最終反映前の検証・実操作・再試行
  ├─ localDatabase          IndexedDB / chrome.storage.local
  └─ cloudSyncService       所有者確認・設定一式のHTTP同期
                                   ↓ （ログイン時のみ）
AWS側：FastAPI → PostgreSQL  （グループ設定一式のGET/PUT）

この図は論理的な責務分担です。どの処理をPopup / Worker / Service Workerのどこへ置くかを確定する実行配置図ではありません。

境界の例

  • UIはユーザーの操作を受けて描画します。分類計算やChrome移動をUIコードへ重複実装しません。
  • mainは処理順を統括し、セッションの状態制限を守ります。
  • classificationModelは分類先のDestinationを返します。Chromeの移動先フォルダIDは決めません。
  • groupServiceはグループと実フォルダの対応を検証します。グループの追加・削除は作業用の仮変更です。
  • applyServiceが、最終反映指示後の検証・移動・結果記録を統括します。
  • ローカルDBはPC固有のフォルダ対応・特徴量・設定一式の同期状態を保存します。すべてをAWSへ送るわけではありません。

モックで並行開発する

モデルやAWSが未完成でも、公開関数の入力・戻り値とエラー条件が定義されていれば、テスト用の固定レスポンスでUIを先に作れます。その際は「モック実行で成功」と「実サービスとの結合で成功」を明確に区別します。
